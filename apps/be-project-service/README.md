# be-project-service

Project CRUD service for the fs-platform.

It is a **resource server**: it never issues tokens. It verifies the RS256 access tokens minted by
[be-identity-service](../be-identity-service/README.md) using that service's public key, and owns its
own PostgreSQL database. Every project is scoped to the `sub` claim of the caller's token.

- NestJS 11 with CQRS (`@nestjs/cqrs`), Prisma 7 and PostgreSQL 18
- RS256 JWT verification via a shared public key (no network call, no JWKS polling)
- Structured JSON logging with `nestjs-pino`, shipped to Loki by Alloy
- OpenAPI docs at `/docs`

---

## Prerequisites

- Node `>=22.12` (`.nvmrc` pins 24 — run `nvm use` from the repo root)
- Docker, for PostgreSQL and the observability stack
- A running [be-identity-service](../be-identity-service/README.md), or at least its RS256 **public** key

---

## Setup

All commands below run from `apps/be-project-service` unless stated otherwise.

### 1. Install dependencies

Dependencies are installed once for the whole monorepo, from the repository root:

```bash
npm install
```

### 2. Start PostgreSQL

From the repository root:

```bash
docker compose up -d project-db
```

This starts `fs-project-db` on host port **5433** (the identity database keeps 5432), with database
`project_db` and user/password `project`/`project`.

### 3. Create the environment file

```bash
cp .env.example .env
```

Every variable is documented in [Configuration](#configuration).

### 4. Copy the identity service's public key

This service verifies tokens, so it needs **only the public half** of be-identity-service's key pair.
Never give it the private key.

If you have not generated a key pair yet, do it in the identity service first:

```bash
cd ../be-identity-service && npm run keys:generate
```

Then copy the value of `JWT_PUBLIC_KEY_B64` from `apps/be-identity-service/.env` into this service's
`.env` verbatim:

```bash
grep '^JWT_PUBLIC_KEY_B64=' ../be-identity-service/.env >> .env
```

`JWT_ISSUER` and `JWT_AUDIENCE` must also match the identity service exactly. Note that `JWT_ISSUER`
stays `http://localhost:3001` — it describes who _minted_ the token, not where this service listens.

### 5. Apply migrations

```bash
npm run db:migrate
```

This also runs `prisma generate`. If you only need the client, run `npm run db:generate`.

## Running

```bash
npm run dev          # watch mode, pretty logs
npm run dev:logs     # watch mode, NDJSON tee'd to logs/be-project-service.ndjson
npm start            # run the compiled output from dist/
```

The service listens on **http://localhost:3002** and serves Swagger UI at
**http://localhost:3002/docs**.

### Verify it works

```bash
# Public, no token required
curl http://localhost:3002/health/ready

# Obtain a token from the identity service, then call a guarded route
TOKEN=$(curl -s -X POST http://localhost:3001/auth/login \
  -H 'content-type: application/json' \
  -d '{"email":"admin@example.com","password":"<password>"}' | jq -r .accessToken)

curl -H "Authorization: Bearer $TOKEN" http://localhost:3002/projects
```

## Endpoints

Every `/projects` route requires `Authorization: Bearer <access token>` and operates only on projects
owned by the token's `sub`. A project belonging to another user responds `404`, never `403`, so the
API does not leak which ids exist.

| Method   | Path            | Auth   | Description                                     |
| -------- | --------------- | ------ | ----------------------------------------------- |
| `GET`    | `/health`       | Public | Liveness probe                                  |
| `GET`    | `/health/ready` | Public | Readiness probe, verifies database connectivity |
| `POST`   | `/projects`     | Bearer | Create a project owned by the caller            |
| `GET`    | `/projects`     | Bearer | List the caller's projects, paginated           |
| `GET`    | `/projects/:id` | Bearer | Return one project                              |
| `PATCH`  | `/projects/:id` | Bearer | Update `title` and/or `description`             |
| `DELETE` | `/projects/:id` | Bearer | Soft-delete a project, returns `204`            |

### Project model

| Field         | Type           | Notes                                                    |
| ------------- | -------------- | -------------------------------------------------------- |
| `id`          | uuid v7        | Generated by the database                                |
| `userId`      | string         | The token's `sub`. Never accepted from the request body  |
| `title`       | string         | Required, trimmed, max 256 characters                    |
| `description` | string \| null | Optional, trimmed, max 1024 characters. `null` clears it |
| `createdAt`   | ISO 8601       | Set on insert                                            |
| `updatedAt`   | ISO 8601       | Maintained by Prisma                                     |

Deletes are soft: a `deletedAt` column is stamped and the row is excluded from every read. The column
is not part of any response.

### Listing and pagination

`GET /projects` accepts:

| Query    | Default | Notes                                       |
| -------- | ------- | ------------------------------------------- |
| `page`   | `1`     | 1-based                                     |
| `limit`  | `20`    | Maximum `100`                               |
| `search` | —       | Case-insensitive substring match on `title` |

It responds with `{ "data": [...], "total": <number>, "page": <number>, "limit": <number> }`, where
`total` counts all matching projects, ignoring pagination.

### Token model

The service accepts an access token when **all** of the following hold:

- `alg` is `RS256` and the signature verifies against `JWT_PUBLIC_KEY_B64` (or
  `JWT_PREVIOUS_PUBLIC_KEY_B64` during a rotation)
- the `kid` header matches one of those keys — the RFC 7638 thumbprint, unless `JWT_KEY_ID` overrides it
- `iss` equals `JWT_ISSUER` and `aud` equals `JWT_AUDIENCE`
- the token has not expired

There is no user lookup: this service has no user table, so a valid token is authoritative about who
the caller is. Revoking a user is the identity service's job, bounded by the access token TTL.

## Testing

```bash
npm test             # unit tests, no database required
npm run test:cov     # unit tests with coverage
npm run test:e2e     # end-to-end, needs a running and migrated database
```

Unit tests mock `PrismaService` with plain objects. The e2e suite mints a throwaway RS256 key pair in
[test/setup-e2e.ts](test/setup-e2e.ts) and signs its own tokens through
[test/tokens.ts](test/tokens.ts), so it never needs the identity service to be running.

## Logging

Logs are structured JSON written to stdout by `nestjs-pino`, configured once in
[src/logging/logging.module.ts](src/logging/logging.module.ts).

- Every line carries `service: "be-project-service"`, `env`, `level` and `req.id`
- `x-request-id` is echoed when the caller supplies a short, opaque value; otherwise one is generated
- Authorization headers, cookies, passwords and tokens are redacted
- `/health` and `/docs` are excluded from request logging
- Request bodies are never logged
- `AllExceptionsFilter` is the only place that logs failures: 4xx as `warn`, 5xx as `error`

Set `LOG_PRETTY=true` for human-readable output locally, and `LOG_LEVEL` to change verbosity.

### Observability stack

```bash
docker compose --profile observability up -d
```

Alloy tails both the compose containers and `logs/*.ndjson`, ships to Loki, and Grafana serves the
[be-project-service dashboard](../../observability/grafana/dashboards/be-project-service.json) at
http://localhost:3000/d/fs-project-logs.

Only `service`, `env` and `level` are Loki labels. `req_id`, `user_id` and `status_code` are
structured metadata — do not promote high-cardinality fields to labels.

## Configuration

Environment variables are validated with zod in [src/config/env.ts](src/config/env.ts) at startup; the
process exits with a readable error if any are missing or malformed.

| Variable                      | Required | Default       | Description                                               |
| ----------------------------- | -------- | ------------- | --------------------------------------------------------- |
| `NODE_ENV`                    | no       | `development` | `development`, `test` or `production`                     |
| `PORT`                        | no       | `3002`        | HTTP port                                                 |
| `SWAGGER_ENABLED`             | no       | `true`        | Set to `false` to disable `/docs`                         |
| `LOG_LEVEL`                   | no       | `info`        | `fatal`…`trace`, or `silent`                              |
| `LOG_PRETTY`                  | no       | `false`       | Human-readable logs; leave unset in deployed environments |
| `DATABASE_URL`                | **yes**  | —             | PostgreSQL connection string                              |
| `JWT_ISSUER`                  | **yes**  | —             | Must equal be-identity-service's `JWT_ISSUER`             |
| `JWT_AUDIENCE`                | **yes**  | —             | Must equal be-identity-service's `JWT_AUDIENCE`           |
| `JWT_PUBLIC_KEY_B64`          | **yes**  | —             | Base64-encoded PEM public key. RSA, at least 2048 bits    |
| `JWT_PREVIOUS_PUBLIC_KEY_B64` | no       | —             | Retired public key, accepted during a rotation            |
| `JWT_KEY_ID`                  | no       | —             | Overrides the RFC 7638 thumbprint used as `kid`           |

`DATABASE_URL` must be set even for `prisma generate`, because `prisma.config.ts` resolves it eagerly.

### Rotating signing keys

Key rotation is driven by be-identity-service. To avoid rejecting tokens that are still valid:

1. Identity generates a new pair and moves its old public key to `JWT_PREVIOUS_PUBLIC_KEY_B64`.
2. Copy **both** `JWT_PUBLIC_KEY_B64` and `JWT_PREVIOUS_PUBLIC_KEY_B64` here and restart this service
   **before** identity starts signing with the new key.
3. Once the longest access token TTL has elapsed, drop `JWT_PREVIOUS_PUBLIC_KEY_B64` from both services.

## Troubleshooting

**Every request returns 401.** The public key, issuer or audience does not match the identity service.
Compare `JWT_ISSUER`, `JWT_AUDIENCE` and `JWT_PUBLIC_KEY_B64` in both `.env` files. Remember that
`JWT_ISSUER` refers to the identity service's address (`http://localhost:3001`), not this service's.

**`Token signed with an unknown key`.** The token's `kid` matches neither the current nor the previous
public key — usually a rotation that was only applied to one service. A blank `JWT_KEY_ID=` in `.env`
is treated as absent, so it will not shadow the thumbprint.

**`JWT_PUBLIC_KEY_B64 must be a base64-encoded PEM block`.** The value was copied as raw PEM. It must
be base64-encoded, which is how `npm run keys:generate` writes it in the identity service.

**Type errors pointing at `src/generated/prisma/`.** The Prisma client is stale. Run
`npm run db:generate`. That directory is generated and git-ignored — never edit it.

**`Invalid environment configuration`.** A variable is missing or malformed; the error lists each
offending key. Blank values in `.env` fall back to defaults rather than failing.

**Migrations fail to connect.** Confirm `fs-project-db` is running and that `DATABASE_URL` points at
port **5433**, not 5432 (that is the identity database).
